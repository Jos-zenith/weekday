# Weekday Scheduling Desk

| File | What it is |
|---|---|
| `Weekday_Scheduling_Desk.xlsx` | The interns' sheet (also loads in Google Sheets). Ships with synthetic demo data and a test clock so the lists are filled. |
| `Weekday_Scheduling_Desk_Plan.docx` | Two-page plan: executive summary (problem, what was built, the most defensible finding, limitations, next experiment), then how much to trust each number (tiers A-F), what 80% would take, and the gates before production. |
| `src/build_desk.py` | Builds the workbook. |
| `src/build_plan.js` | Builds the plan document. |
| `analysis/scenarios.py` | Path-to-80% grid and cost sensitivity. Plain arithmetic; writes `analysis/scenarios.json`. |
| `analysis/sim2.py` | Candidate-behaviour model; used only to generate the demo data and the dry run's hidden truth. |
| `tests/check_workbook.py` | Google Sheets function audit, script wording check, formula-error scan, WhatsApp link lengths. |
| `tests/test_request_tracking.py` | 29 checks that each request ID survives from INPUT to booking: repeated rounds, several requests per candidate, duplicates, partial answers, links, wrong IDs. |
| `tests/dry_run.py` | Synthetic dry run: a bot works one simulated day using only what the intern tabs show, with or without the evening-message pilot. Its result file keeps pass/fail mechanics checks apart from simulated outcomes, which are not evidence. |
| `tests/SHEETS_ACCEPTANCE.md` | The 11-check Google Sheets test to run before go-live. **Not run yet.** |
| `tests/output/` | Dry-run workbooks and results (regenerated by the commands below). |

**Status: not production-ready.** That needs the 30-minute usability test and `tests/SHEETS_ACCEPTANCE.md` to pass (plan, section 6).

## Rebuild and test

```
python src/build_desk.py          # writes Weekday_Scheduling_Desk.xlsx and tests/output/truth.json
python tests/check_workbook.py    # needs Excel on Windows (runs in its own Excel process)
python tests/test_request_tracking.py
python tests/dry_run.py                     # with the evening-message pilot
EVENING_MSG=0 python tests/dry_run.py       # without it
python analysis/scenarios.py
node src/build_plan.js            # needs the npm package "docx"
```

## Tabs

- **Interns:** START HERE, RAM, SHYAM, LOG.
- **Lead:** DASHBOARD (live results, day-1 readout, path to target, cost), MESSAGES (evening WhatsApp pilot), PARTNERS, INPUT, SETTINGS.
- **Hidden:** DESK (the engine), LISTS (outcome codes and message text).

## Go live

1. SETTINGS: clear the test clock (B3).
2. INPUT: delete the demo rows and paste the partner sheet (columns A-I). Column K gives every request its ID; paste the partner's own IDs over it if they have them. Add rows at the bottom only, and never sort INPUT once logging has started.
3. PARTNERS: list each company with its booking link. Set "We may book for candidates?" to YES only with the partner's written OK.
4. Run `tests/SHEETS_ACCEPTANCE.md`. Set Sheets to recalculate every minute, and protect the lead tabs.
5. Run the 30-minute test with two people who have never seen the file (plan, section 6).
6. Evening WhatsApp: leave SETTINGS B22 at NO until candidate opt-in, a provider account and approved templates exist (plan, section 5).
